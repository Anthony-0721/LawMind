# LawMind 简历与面试表达

## 1. 项目定位

面试时不要把 LawMind 只描述成“做一个法律咨询机器人”。更准确的表达：

> LawMind 是一个面向律所对外咨询场景的多 Agent 法律咨询系统，包含法律意图与风险识别、RAG 法律知识库、PostgreSQL 业务数据、4 类 Agent 编排、律师推荐、留资/转人工、工作人员控制台以及 LLM-as-Judge 评测闭环。

## 2. 一句话版本

```text
设计并实现了一个面向律师事务的多 Agent 智能法律咨询系统，支持 7 类法律领域识别、刑事/民事风险分析、法律知识检索、律师推荐与人工升级，并将咨询记录、律师、FAQ 统一管理到 PostgreSQL。系统保留多 Agent 结构化路由、动态 Skills、监控降权和端到端评测能力。
```

## 3. 简历项目经历建议

### 版本 A：AI 应用工程

```text

- 设计 7 类法律领域与 7 类风险信号识别，输出 legal_domain、case_stage、blood_alcohol、disputed_amount、risk_flags 等结构化字段，为 Agent 路由和转人工提供依据。

- 将法律风险与人工升级链路闭环，对外公开 escalated 标记、律师推荐、留资和转人工接口，同时隐藏 agent_type、tools、routing_reason 等内部信息。
- 实现律所工作人员控制台，支持咨询记录、律师、FAQ 和知识库同步管理，并对手机号等 PII 做脱敏。

```

## 4. 面试介绍模板

```text
“这个项目是面向律所对外咨询场景的多 Agent 法律咨询系统。用户输入问题后，系统会先识别法律领域和风险信号，再根据是否涉及刑事、民事、律所服务或紧急情况，把请求路由到对应 Agent。

比如醉驾，会走刑事 Agent，系统会检索危险驾驶罪、80mg/100ml、立案标准、血检程序、取保候审等内容，并提示用户补充血液酒精含量、是否发生事故、目前处于什么阶段。如果检测到刑事拘留或即将开庭，会直接触发转人工。

同时，系统没有只做一个聊天接口，而是把 FAQ、律师推荐、客户留资、转人工、咨询记录和工作人员管理都串起来了。对外响应做了白名单，隐藏内部 Agent 和工具信息，只公开 escalated、legal_domain、risk_flags、律师推荐等字段。”

```

## 5. 面试官可能问的问题

### 为什么不用一个大模型直接回答？

因为法律咨询不能只靠一段 prompt。不同领域需要不同风险规则、不同工具和不同升级边界；一个大 prompt 会越来越难维护，也无法形成工具白名单和结构化业务闭环。

### 为什么不是 7 个 Agent？

7 个领域属于业务分类，但 Agent 更适合按能力边界拆分。刑事共用 CriminalDefenseAgent，民事共用 CivilConsultationAgent。复合问题通过主辅 Agent 并行处理。

### 知识库怎么管理？

PostgreSQL 是事实源，FAQ 在工作人员页管理；通过 FaqSyncService 同步到 ChromaDB。这样业务数据可维护，检索仍有语义能力。

### 对外为什么隐藏 agent_type？

外部客户不需要知道内部路由。隐藏内部信息可以降低接口耦合，避免内部重构影响前端，也避免暴露系统结构。

### 转人工怎么标记？

Agent 内部使用 `escalated`，公开响应也返回 `escalated: true`。客户通过 `/api/law/transfer` 提交联系信息后，PostgreSQL 中记录 `source=transfer`。

### 如何保证法律回复不越界？

- 所有公开响应统一追加免责声明。
- Skills 禁止承诺胜诉、取保、无罪、缓刑、赔偿金额。
- 高风险场景直接转人工。
- 不收集非必要的身份证号、银行卡号、密码等。

## 6. 不建议说的话

- 不要声称“完全替代律师”。
- 不要在没有标注集/压测数据时声称“准确率 99%”。
- 不要把它描述成“企业级通用大模型平台”。
- 不要隐去多 Agent 架构、RAG、记忆、工具、监控和评测，只讲“调 API 问答”。
