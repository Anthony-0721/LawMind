# LawMind 技术亮点

## 结论

LawMind 的核心技术不是“调用大模型回答”，而是：

```text
理解 -> 路由 -> 检索 -> 执行 -> 记忆 -> 业务闭环 -> 监控 -> 评测
```

| 能力 | 关键模块 | 价值 |
| --- | --- | --- |
| 法律意图与风险识别 | `backend/core/law_domain.py`、`core/intent_recognizer.py` | 将法律问题转成结构化意图、实体和风险信号 |
| 多 Agent 编排 | `backend/agents/agent_orchestrator.py` | 支持刑事、民事、接待、升级 4 类角色 |
| 工具与知识检索 | `backend/agents/tools.py`、`mcp/knowledge_base.py` | Agent 具备可复用但有边界的法律工具 |
| PostgreSQL 事实源 | `backend/db/`、`services/` | 保存咨询、律师、FAQ，并驱动 ChromaDB 同步 |
| 三级记忆 | `backend/memory/conversation_memory.py` | Redis 工作记忆 + ChromaDB 情景记忆/用户画像 |
| 动态 Skills | `backend/core/skill_loader.py` | 律所业务规范可维护、可热加载 |
| 对外白名单与转人工 | `backend/api/law_routes.py` | 隐藏内部 Agent 信息，公开 `escalated` 标记 |
| Monitor / Evaluator | `backend/monitor/`、`evaluation/` | 在线监控和 LLM-as-Judge 评测 |
| Docker Compose | `docker-compose.yml` | 联合部署 Nginx + Frontend + API + PostgreSQL + Redis + ChromaDB |

## 亮点一：法律领域与风险识别

`LawIntent` 当前支持：

```text
dangerous_driving
criminal_defense
labor_dispute
marriage_family
contract_dispute
traffic_accident
civil_loan
lawyer_appointment
law_firm_service
other
```

前 7 类是核心个人法律领域，后 3 类是预约律师、律所服务和暂不明确。

`LawRiskFlag` 不止是“紧急”，还包括：

```text
detention          已刑事拘留
court_soon         即将开庭
injury             已发生人身伤亡
traffic_accident   发生交通事故
filed              已立案
prosecution        审查起诉阶段
no_lawyer          无律师代理
```

系统还会抽取：

```text
case_stage
blood_alcohol
city
incident_time
disputed_amount
party_role
traffic_accident
injury_or_death
has_lawyer
```

## 亮点二：结构化多 Agent 路由

`AgentOrchestrator` 会生成 `RoutingDecision`：

```text
primary_agent
supporting_agents
reason
confidence
```

路由顺序：

1. 刑事拘留、即将开庭、CRITICAL -> EscalationAgent
2. 预约律师/转人工 -> EscalationAgent
3. 刑事意图 -> CriminalDefenseAgent
4. 民事意图 -> CivilConsultationAgent
5. 律所服务/其他 -> ReceptionAgent
6. 复合问题 -> 主 Agent + 辅助 Agent 并行

每个 Agent 都有独立的 `AgentProfile`：

```text
role
mission
workflow
input_contract
output_contract
handoff_conditions
tool_scope
```

所以 Agent 的差异不是“换一个 system prompt”，而是职责、工具边界和升级条件都不同。

## 亮点三：法律知识库与 FAQ 同步

当前知识库采用 PostgreSQL 作为事实源：

```sql
law_faq
  -> FaqSyncService
  -> ChromaDB law_knowledge_base
```

- FAQ 可在工作人员页新增、编辑、删除和启停。
- 修改后通过 `faq_sync_service` 同步到 ChromaDB。
- 旧向量先删除，避免残留。
- `sync_status` 表示同步状态。

当前知识库包含：

- 20 条官方来源法条 FAQ
- 69 条 FAQ
- 8 份领域摘要
- ChromaDB `law_knowledge_base`

## 亮点四：三层记忆

| 层 | 存储 | 作用 |
| --- | --- | --- |
| 工作记忆 | Redis | 当前会话最近消息 |
| 情景记忆 | ChromaDB `episodic` | 历史摘要，跨轮线索 |
| 用户画像 | ChromaDB `user_profile` | 用户需求和长期上下文 |

工作记忆超过阈值后会自动压缩，避免上下文无限增长。

## 亮点五：动态 Skills

```text
backend/skills/law_firm/
  front_desk_reception/       律所前台接待
  criminal_consultation/      刑事咨询
  civil_consultation/         民事咨询
  escalation_and_intake/      转人工与留资
```

Skills 通过 front matter 声明：

```text
agents: reception
keywords: ...
enabled: true
```

系统按 Agent 类型和关键词决定是否注入，因此不同 Agent 之间的规范不会互相污染。

## 亮点六：对外安全边界

`LawChatPublicResponse` 是公开接口白名单：

```python
response
intent
intent_group
legal_domain
case_stage
risk_flags
escalated
missing_facts
recommended_lawyers
consultation_draft_id
request_id
conversation_id
session_token
```

以下信息不会返回给外部客户：

```text
agent_type
primary_agent
supporting_agents
tools_used
routing_reason
entities
latency_ms
tool_traces
```

但系统仍公开 `escalated`，让前端能明确知道是否建议转人工。

## 亮点七：可评测

- 内置法律领域评测用例
- LLM-as-Judge 回复质量评分
- 归档基线与运行时基线分离
- 支持回归检测
- 后端 302 项测试

## 一句话总结

LawMind 是一个可观测、可评测、带业务闭环和人工升级路径的法律 Agent 系统，而不是单纯接了大模型的聊天 Demo。
